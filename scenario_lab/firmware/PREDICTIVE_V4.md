# v4 트레이: 수평 유지 + 예정 주행 명령 선행 보정

사용자가 제공한 `esp32_level_apparent_v4.ino`를
`esp32_level_apparent_v4/`에 보존했다. 파생 소스는
`esp32_level_predictive_v4/esp32_level_predictive_v4.ino`이며
`python3 make_predictive_v4.py`로 재생성한다.

기존 PI 제어, 영점 Preferences 저장, 축 부호, 속도·가속도 제한,
평활 필터, 겉보기 중력 모드 H/J를 유지한다.

- MODE=4: ESP32가 BNO055로 계속 수평 유지 (`h`).
- MODE=5/6: 기존 H/J 겉보기 중력 정렬. 앱 예측 모드와 다르다.
- MODE=7: 앱의 `@T,roll,pitch\n` 목표각을 IMU 피드백으로 추종.
- PROTO=2, FIRMWARE=APPARENT_V4_FF, PREDICT_MODE=7을 보고한다.
- 목표는 저장된 실제 수평 대비 트레이 IMU 각도이며 ±8° 이내다.
- 500ms 목표 만료 시 MODE=4 / 목표 0°로 복귀한다.
- IMU 만료 시 자동제어를 중단하고 마지막 PWM을 유지한다.
- 부팅만으로 서보를 켜지 않으며 영점·방향 확인을 자동 생성하지 않는다.

앱의 기존 Predictor는 예정 명령을 0.20초 전개해 선형가속도와
회전 가속 성분에 해당하는 목표각을 계산한다. 기본 각도 제한은 5°,
변화율은 12°/s이며 실제 장치의 최적값은 아직 측정하지 않았다.
시나리오의 계획된 급정지는 앞으로의 정지 명령을 이용한다.
수동 키 해제, 비상정지, 외부 충격의 발생 시점은 예측할 수 없다.
그 경우 모터 정지를 선행 보정을 위해 지연시키지 않는다.
기존 지도 화면의 Jetson L자 주행과 사람 추종에는 이 예측을 활성화하지 않는다.
이들은 별도 제어 경로이므로 추가 연동·검증이 필요하다.

ESP32와 IMU가 동일한 장착 상태이고 영점이 저장돼 있어도,
실제 방향 확인은 운영자가 수행해야 한다. 새 업로드 시 NVS를 지우지 않는다.
확인된 보드의 앱 파티션만 갱신하면 기존 영점·방향 설정과
부트로더·파티션 테이블을 보존할 수 있다. 업로드 전 전체 플래시를 백업한다.

검사:

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest -q \
  scenario_lab/tests/test_tray.py scenario_lab/tests/test_tray_v4.py \
  scenario_lab/tests/test_predictive_v4_firmware.py \
  scenario_lab/tests/test_server.py scenario_lab/tests/test_operator_control.py
```

Python 통신·가상 로봇 테스트와 실제 C++ 프레임 파서/워치독을
가짜 시계로 실행한다. 실물 출렁임·물 유출량 감소를 검증한 결과는 아니다.

## 2026-11-13 실물 적용 기록

ESP32-S3 MAC 44:bd:8d:75:03:18, 16MB quad flash를 식별했다.
전체 플래시 백업 SHA256은
`517649f40213e11fc9b96e84cbb4d0f3c8f6de85a8e98513997e5bb6e52a3480`.
기존 OTA seq=1/CRC를 확인해 app0(0x10000)만 업로드했고 쓰기 해시가 일치했다.
기존 영점 offR=-5.47/offP=-4.63, home=1500/1500, dir=1/1을 수신했다.
사용자가 동일 장치에서 방향 확인이 완료됐다고 확인한 뒤 서보와 수평 유지를 요청했다.
PWM은 R1469→1243 / P1490→1423으로 바뀌었지만 6초 동안 IMU는
R3.12°/P1.14°로 변하지 않아 자동 보정을 OFF(PWM 유지)로 돌렸다.
서보 전원·기구 연결·IMU 장착 상태 확인이 남았다. 예측 보정을 켠 채 주행하지 않았다.
원본 전체 백업, 업로드 로그와 장치 상태는
`scenario_lab/backups/predictive_v4_20261113/`에 보관했다.

### 현재 PWM 출력과 남은 실물 확인

현재 출력 드라이버는 Arduino-ESP32 `ledcAttach/ledcWrite`를 직접 사용한다.
100Hz, 14비트이며 연결/쓰기 실패를 확인한다. 최초 듀티 갱신 전에 잘못 실패로
판정하지 않도록 두 PWM 주기 뒤에 주파수를 확인한다.
시작 확인 시점의 문제와 기존 래퍼의 상태 표시 문제를 보완했지만,
기존 라이브러리만이 실제 무동작의 원인이었다고 확인한 것은 아니다.

현재 수정본은 app0에 업로드됐고 쓰기 해시를 검증했다. MCU 진단에서 두 채널 모두
100Hz이고 1500us에서 듀티 2458이다. Roll을 1540us로 바꾸면 듀티 2523으로
변하지만 IMU는 R2.60°/P1.16°로 그대로였다. 이는 MCU 설정값의 검증이며
전선에서의 실제 파형이나 서보 전압 측정은 아니다.
BNO 상태 SYS=5, SELFTEST=15, ERROR=0이고 읽기 횟수는 증가한다.
사용자는 전원 ON, IMU 트레이 장착, 작은 Roll 조정에도 실제 움직임 없음을 확인했다.

자동 보정은 OFF이고 시험 뒤 두 출력을 기존 중앙값 1500us로 복귀시켰다.
GPIO18(Roll)/GPIO17(Pitch) 신호선, 서보 전원과 ESP32의 공통 GND,
서보 커넥터의 정격 전원 확인이 남았다. 배선 확인 없이 추가 주행/자동 보정을 하지 않는다.
최종 코드의 모의 드라이버/프로토콜/API 등 94개 검사와 Arduino 컴파일은 통과했다.

## 마지막 장치 상태: 원본 복구 완료

사용자가 Jetson C-C 연결에서 ESP32 빨간 LED가 꺼지고 노트북 연결에서는 켜진다고 보고했다.
노트북 /dev/ttyACM0에서 동일 MAC 44:bd:8d:75:03:18을 확인했다.
전체 백업의 원래 app0 0x10000~0x14FFFF를 그대로 복구했고 쓰기 해시가 일치했다.
실험용 예측/직접 PWM 빌드는 현재 보드에 없으며 원래 v4로 돌아갔다.
NVS 영점, 부트로더, 파티션은 유지했다. 아직 원본으로 실제 서보 재동작을 확인하지 않았다.
USB 전원 경로를 안정화한 다음 원래 단독 동작을 기준으로 비교해야 한다.

### 노트북 원본 단독 시험: 자세 확인 대기

동일 USB 장치에서 원본 `APPARENT_V4`, MODE=0, 두 서보 OFF,
저장 영점과 정상 상태 응답을 확인했다. 그러나 서보를 켜기 전부터
R=2.99°, P=-65.24°로 수신되어 수동 시험의 자세 범위를 벗어났다.
시험은 상태 요청 `p`만 전송하고 종료했다. 서보 활성화/이동/자동 보정/
영점 변경 명령은 전송하지 않았다. 실제 트레이 및 IMU 자세 확인이 필요하다.
원시 응답은 `backups/predictive_v4_20261113/original_laptop_manual_test.jsonl`에 있다.

사용자는 실제 트레이/IMU가 크게 기울어져 있으며 현재 모터 배터리를
연결하지 않았다고 확인했다. 이 배터리가 트레이 서보에도 공급되는지는
아직 확인되지 않았다. USB만으로 서보 전원까지 정상이라고 판단하지 않는다.
상태만 다시 읽은 결과 R=3.04°, P=-65.08°, MODE=0, 두 서보 OFF였다.
수평에 가까운 자세 및 실제 서보 전원 경로를 확인한 뒤 동작 시험을 이어간다.
